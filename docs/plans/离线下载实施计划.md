# 离线下载实施计划

本文档基于 `docs/drission-cloud-driver-offline-plan.md`，并结合当前项目代码状态，整理面向 `get-magnet` 对接的离线下载能力落地方案。

## 当前代码状态

### 已具备

- 路由已覆盖离线下载主链路：
  - `GET /health`
  - `GET /drivers`
  - `GET /drivers/:platform/capabilities`
  - `POST /drivers/:platform/offline/add`
  - `GET /drivers/:platform/offline/tasks`
  - `GET /drivers/:platform/offline/tasks/:id`
  - `DELETE /drivers/:platform/offline/tasks/:id`
  - 文件系统和媒体 URL 相关路由也已注册。
- Handler 已使用统一响应格式：
  - `code`
  - `message`
  - `data`
  - `error`
- `X-Profile-ID` 已作为 Driver API 的 Profile 来源，缺失时会返回业务错误。
- 115 Driver 已能：
  - 从浏览器 Profile 获取 115 cookie。
  - 初始化并缓存 `Pan115Client`。
  - 提交离线任务。
  - 查询离线任务。
  - 删除离线任务。
  - 列出离线任务。
  - 创建目录、列表、搜索、删除、移动、重命名、下载直链。
- 已有基础单元测试：
  - 配置加载。
  - Driver 注册表。
  - 统一响应。
  - Health handler。

### 主要缺口

- 离线任务类型已迁移为 `OfflineTask`，并包含文档要求的核心字段。
- `AddTaskRequest` 已支持 `category`、`client_task_id`、`metadata`。
- 统一任务 ID 与状态映射已完成：
  - 115 running 已映射为 `running`。
  - `task_id` 已使用 `platform:provider_task_id` 格式。
- `offline/add` 已支持自动确认并逐级创建 `save_path`。
- 查询任务状态时只查 115 当前任务列表第一页。
- 任务完成后已按 `FileId`、`DirId`、任务名搜索尽量补齐 `files`。
- 列表响应已调整为 `items` + `total`。
- 删除任务响应已返回 `task_id` + `deleted`。
- 媒体 URL 已支持 `file_id` 优先，仍兼容 `path`。
- 暂无幂等处理和任务持久化。

## 目标契约

第一阶段以 `get-magnet` 最小可用为目标：

- `GET /health` 返回成功。
- `POST /drivers/:platform/offline/add` 成功返回 `data.task_id`。
- `GET /drivers/:platform/offline/tasks/:id` 成功返回 `data.status`。
- `status` 只能是：
  - `pending`
  - `running`
  - `completed`
  - `failed`
  - `canceled`
  - `unknown`

后续再完善：

- 完成文件列表。
- 幂等。
- 持久化。
- 多平台 Driver。

## 阶段 1：固定统一离线类型

状态：已完成。

目标：先把对外数据模型固定，避免后续 handler 和 Driver 各自返回临时结构。

### 修改点

- 更新 `internal/drivers/types.go`。
- 引入 `TaskStatus` 枚举类型。
- 新增或替换离线任务结构：

```go
type AddTaskRequest struct {
    URL          string            `json:"url" binding:"required"`
    Category     string            `json:"category,omitempty"`
    SavePath     string            `json:"save_path,omitempty"`
    ClientTaskID string            `json:"client_task_id,omitempty"`
    Metadata     map[string]string `json:"metadata,omitempty"`
}

type OfflineTask struct {
    TaskID         string     `json:"task_id"`
    ProviderTaskID string     `json:"provider_task_id,omitempty"`
    Status         TaskStatus `json:"status"`
    Name           string     `json:"name,omitempty"`
    Progress       float64    `json:"progress,omitempty"`
    SavePath       string     `json:"save_path,omitempty"`
    ErrorCode      string     `json:"error_code,omitempty"`
    ErrorMessage   string     `json:"error_message,omitempty"`
    Files          []FileInfo `json:"files,omitempty"`
    CreatedAt      time.Time  `json:"created_at,omitempty"`
    UpdatedAt      time.Time  `json:"updated_at,omitempty"`
}

type OfflineTaskList struct {
    Items []OfflineTask `json:"items"`
    Total int           `json:"total"`
}
```

- `TaskStatus` 旧结构可以先保留为兼容别名，或直接迁移所有引用到 `OfflineTask`。

### 验收

- `offline/add` 返回 `data.task_id`、`data.provider_task_id`、`data.status`。
- `offline/tasks/:id` 返回 `data.status`。
- `offline/tasks` 返回 `data.items` 和 `data.total`。
- `go test ./...` 通过。

## 阶段 2：统一任务 ID 与状态映射

状态：已完成。

目标：内部统一 ID 和状态，不把平台原始 ID 当作唯一契约。

### 修改点

- 新增任务 ID 工具，建议位置：
  - `internal/drivers/taskid.go`

规则：

```text
task_id = platform + ":" + provider_task_id
```

- 新增解析方法：
  - `BuildTaskID(platform, providerTaskID string) string`
  - `ParseTaskID(taskID string) (platform string, providerTaskID string, ok bool)`

- 115 Driver 查询/删除时支持两种输入：
  - `115:<hash>`
  - `<hash>`

- 修正 115 状态映射：
  - `IsTodo()` -> `pending`
  - `IsRunning()` -> `running`
  - `IsDone()` -> `completed`
  - `IsFailed()` -> `failed`
  - 未知 -> `unknown`

### 验收

- `offline/add` 返回类似 `115:<info_hash>` 的统一 `task_id`。
- `offline/tasks/:id` 使用统一 `task_id` 可查询。
- `running` 不再返回 `downloading`。
- 单元测试覆盖 task id 生成/解析和状态映射。

## 阶段 3：保存目录自动确认与创建

状态：已完成。

目标：`offline/add` 收到 `save_path` 后，确保目标目录存在，再提交离线任务。

### 修改点

- 在 115 Driver 中新增目录确保方法：

```go
func (d *Driver) ensureDir(ctx context.Context, client *driver.Pan115Client, remotePath string) (string, error)
```

行为：

- `save_path` 为空：使用根目录。
- 目录已存在：返回目录 ID。
- 目录不存在：按路径逐级创建。
- 任一级创建失败：返回业务错误，停止提交任务。

- `Mkdir` handler 建议兼容文档中的请求格式：

```json
{
  "path": "/get-magnet/JavDB/2026-05-30"
}
```

同时保留当前格式：

```json
{
  "parent_path": "/get-magnet/JavDB",
  "name": "2026-05-30"
}
```

### 验收

- `offline/add` 使用不存在的 `save_path` 时会自动创建目录。
- 创建目录失败时不会提交 115 离线任务。
- `POST /drivers/115/fs/mkdir` 支持 `path`。

## 阶段 4：完成任务文件定位

状态：已完成。

目标：任务完成后尽可能返回 `files`，供 `get-magnet` 或后续流程使用。

### 修改点

115 SDK 的离线任务包含以下可能有用字段：

- `Name`
- `Size`
- `FileId`
- `DirId`
- `DelFileId`
- `InfoHash`

定位策略：

1. 如果 115 任务返回 `FileId`，优先用 `GetFile(fileID)` 获取文件信息。
2. 如果 `FileId` 为空但有 `DirId`，列出目录并按任务名匹配。
3. 如果前两者失败，使用 `Search(keyword)` 按任务名搜索。
4. 如果仍找不到，状态保持 `completed`，`files` 返回空数组。

### 验收

- `completed` 任务响应中包含 `files` 字段。
- 文件条目至少包含：
  - `id`
  - `name`
  - `path`
  - `size`
  - `is_dir`
- 找不到文件时不把任务错误地标记为 `failed`。

## 阶段 5：Handler 响应契约调整

状态：已完成。

目标：让 HTTP 返回结构严格贴合离线计划文档。

### 修改点

- `GetCapabilities` 当前返回：

```json
{
  "platform": "115",
  "capabilities": {}
}
```

建议改为兼容扁平字段，同时保留 `capabilities`：

```json
{
  "platform": "115",
  "offline_download": true,
  "fs_list": true,
  "fs_search": true,
  "media_url": true,
  "capabilities": {}
}
```

- `ListOfflineTasks` 返回：

```json
{
  "items": [],
  "total": 0
}
```

- `RemoveOfflineTask` 返回：

```json
{
  "task_id": "...",
  "deleted": true
}
```

- `GetDownloadURL` 支持：
  - `file_id`
  - `path`

第一优先级为 `file_id`。

### 验收

- `get-magnet` 只读取 `data.task_id` 和 `data.status` 即可完成首轮对接。
- 文档中的示例响应能被当前接口返回结构覆盖。

## 阶段 6：错误码补齐

状态：已完成。

目标：补齐离线下载和 Profile 登录态相关业务错误，减少调用方解析字符串。

### 修改点

- 更新 `internal/pkg/errcode/errcode.go`。

已按方案 A 新增：

```go
ErrInvalidRequest     = &Code{Value: 40020, Message: "invalid request"}
ErrProfileNotLoggedIn = &Code{Value: 40110, Message: "profile is not logged in"}
ErrTaskNotFound       = &Code{Value: 40412, Message: "offline task not found"}
ErrIdempotentConflict = &Code{Value: 40910, Message: "idempotent task already exists"}
ErrPlatformState      = &Code{Value: 50013, Message: "platform state cannot be parsed"}
```

注意当前已有错误码里 `40101` 和 `40901` 被用户相关错误占用。建议二选一：

- 方案 A：保留现有错误码，不强行按文档数字对齐，只保证语义稳定。
- 方案 B：重新规划错误码段，将用户相关旧码移出当前项目不用的范围。

已选择方案 A，避免为了尚未使用的用户错误码做破坏性调整。

### 验收

- 登录态失效返回稳定业务码。
- 任务不存在返回稳定业务码。
- 平台执行失败和平台状态无法解析可以区分。

## 阶段 7：幂等与内存任务仓库

目标：支持 `client_task_id`，降低重复提交磁力任务风险。

### 修改点

- 新增任务仓库接口，建议位置：
  - `internal/offline/store.go`

第一阶段使用内存实现：

```go
type Store interface {
    Put(task OfflineTaskRecord) error
    Get(taskID string) (OfflineTaskRecord, bool)
    GetByClientTask(platform, profileID, clientTaskID string) (OfflineTaskRecord, bool)
    Update(task OfflineTaskRecord) error
}
```

- `DriverHandler` 或新增 `OfflineService` 负责：
  - 检查 `client_task_id`。
  - 命中历史任务时直接返回当前任务状态。
  - 未命中时调用 Driver 提交，再写入 store。

### 验收

- 同一 `platform + profile_id + client_task_id` 重复提交不会创建重复 115 任务。
- 服务进程内重复调用能返回同一个 `task_id`。

## 阶段 8：持久化任务仓库

目标：服务重启后仍能查询历史任务，满足长期运行需要。

### 修改点

- 当前项目没有数据库模块。建议先新增轻量 SQLite 或 BoltDB 存储，减少部署复杂度。
- 新增配置：

```yaml
offline:
  store:
    driver: "memory" # memory | sqlite | boltdb
    dsn: "./data/offline_tasks.db"
```

- 后续如项目引入 GORM/PostgreSQL，再迁移到关系数据库。

### 验收

- 重启服务后，使用旧 `task_id` 仍能查询到本地记录。
- 如果平台仍有任务记录，能刷新最新状态。
